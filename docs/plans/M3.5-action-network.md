# M3.5 — Action-Gated Network Discovery

Goal: replace passive 30-second auto-polling of global endpoints with a system where
**only in-game actions trigger network operations**. The network observatory becomes a
map you discover through gameplay — attack, gather, build, craft, and explore to reveal
latencies to worldwide hosts.

Prereq: M3 (`v0.17-m3-danger-gold`) merged — network observatory panel with sparklines,
realm card, modifiers, danger level, and the basic endpoint probe infrastructure exists.

## Design

### Core rule: only attacks make HTTP fetch() calls
Attacks are the "active" network operation — they fire a real `fetch()` to a random
endpoint from the attack pool and the measured RTT modulates attack speed. All other
actions sample **passive browser APIs** (zero HTTP requests) at action time:

| Action | Network operation | What it samples | Game effect |
|--------|-------------------|-----------------|-------------|
| **Attack** | `fetch()` to random endpoint from attack pool | Real RTT to global host | Attack speed modulated by probe RTT |
| **Gather** | `navigator.connection.downlink` snapshot | Bandwidth at gather moment | — (already drives sim speed) |
| **Build** | Performance API re-read (DNS/TCP/TLS) | Connection anchor timing | — (informational) |
| **Craft** | Jitter snapshot (RTT variance) | Connection stability | — (informational) |
| **Damage** | `navigator.connection.effectiveType` snapshot | Connection tier when hit | — (informational) |
| **Economy** | Already bandwidth-driven | — | — |
| **Explore** | Re-sample connection chain | Fresh route timing | — (informational) |
| **Survive night** | RTT drift (dawn − dusk RTT delta) | Overnight degradation | — (informational) |

### Attack pool (the only HTTP-fetching action)
6 endpoints randomly selected per swing, cooldown 15s:

| Endpoint | Region | Hint |
|----------|--------|------|
| Yandex 🇷🇺 | Europe | Russian search giant — signals crossing hostile territory |
| Naver 🇰🇷 | Asia-Pacific | Korean portal — victory beacons on the peninsula |
| Baidu 🇨🇳 | Asia-Pacific | Chinese search engine — the eastern front |
| Yahoo JP 🇯🇵 | Asia-Pacific | Japanese web portal — far east battle lines |
| Cloudflare 🌐 | Global Anycast | Global CDN edge — your strikes echo through the shield network |
| Microsoft 🇺🇸 | Americas | Cloud backbone — combat data routes through Redmond |

Same endpoint won't be picked twice in a row. Concurrent probes to different URLs allowed.

### Other action pools (passive, zero-request)
Gather, build, craft, damage, economy, explore, and survive_night each have themed
pools of 3–6 endpoints defined in `ACTION_PROBE_POOLS`. These are currently
**informational only** — the observatory shows them but they don't drive game mechanics
yet. Future: each action could sample its specific passive metric at probe time.

Full pool definitions in `src/game/data/network.ts` → `ACTION_PROBE_POOLS`.

### Attack speed ← probe RTT (the closed loop)
When an attack fires a probe:
1. `fetch()` to random endpoint from attack pool (fire-and-forget, no-cors)
2. RTT measured via `performance.now()` delta
3. Result merged into `snap.endpointProbes`, endpoint marked discovered
4. **Next attack's speed** modulated by the most recent probe RTT:
   - Low RTT (<30ms, nearby CDN) → fast swings (0.8× windup/recovery)
   - Medium RTT (30–120ms) → normal swings (1.0×)
   - High RTT (>120ms, far continent) → heavy swings (1.3× windup/recovery)

This creates a natural rhythm: first swing probes, second swing feels the result.

### Observatory
- **Discovered endpoints** show flag emoji + color-coded latency bar + RTT in ms
- **Undiscovered endpoints** show 🔒 `???` + endpoint description hint
- Hints are per-endpoint (describe what the host IS), not per-action
- Network map groups by region (Global Anycast, Africa, Asia-Pacific, Europe, Americas)
- IP/ISP/geo/ASN/colo/WARP identity card loads passively on init (not action-gated)

## ✅ M3.6v2 — Sync RTT → Damage + Resonance Crits (2026-07-16)

**Reworked** because the original attack-speed modulation felt "wonky" — the async probe
fed back to the NEXT swing, not the current one, and speed changes were too subtle.

**New design:**
- **Damage** = sync `navigator.connection.rtt` → immediate damage multiplier (no async delay)
  - <20ms → 1.4×, 20-40ms → 1.2×, 40-80ms → 1.05×, 80-200ms → 1.0×, 200-400ms → 0.85×, >400ms → 0.7×
- **Resonance crits** = if an attack probe resolves during windup with RTT <30ms → 1.5× bonus
- **Attack volley** = every swing fires 3 probes to random endpoints from ALL pools (no cooldown)
- **Observatory** shows ⚔ Damage Mod row with sync RTT + multiplier + resonance label
- Removed attack speed modulation from `envelope()` — soul level is the only speed factor now

**Files changed:** `network.ts` (systems), `combat.ts`, `main.ts`, `data/network.ts`
**Verification:** typecheck ✅ · build ✅ (486 KB) · regression 70/70 ✅ · live test ✅

## Next: M3.6 — Attack Speed ← Probe RTT

Close the loop: the RTT measured by the attack's own `fetch()` modulates the NEXT
swing's windup/recovery duration. Low latency = snappy. High latency = heavy.

Also: define the passive metric sampling for other action pools (gather→downlink,
build→Performance API, craft→jitter, etc.) and wire them into the observatory so
every action contributes a data point even though only attacks make HTTP requests.

### Implementation brief

**Step 1 — Store last probe RTT on NetworkSystem**
- Add `lastAttackRtt: number = 50` field (default 50ms = 1.0× multiplier)
- In `probeSingleEndpoint()`, when the probe completes and the action was `attack`:
  set `this.lastAttackRtt = rtt` (use the measured RTT, clamp 1–2000ms)
- Expose via `getAttackSpeedMul(): number`:
  - RTT < 30ms → 0.8 (fast, nearby CDN edge)
  - RTT 30–120ms → 1.0 (normal)
  - RTT > 120ms → 1.3 (heavy, far continent)
  - Use smooth interpolation between bands, not hard cutoffs

**Step 2 — Wire into CombatSystem.envelope()**
- In `CombatSystem.envelope()`, read `net.getAttackSpeedMul()` 
- Multiply `windup`, `active`, `recovery` by the multiplier
- First swing of session uses default 1.0× (no probe completed yet)
- Add `attackSpeedMul` to `NW.NET` mappings table so it shows in observatory

**Step 3 — Passive metric sampling for other actions**
- Add `samplePassive(action: string)` to NetworkSystem:
  - `gather` → snapshot `navigator.connection.downlink`, store as `lastGatherBw`
  - `build` → re-read Performance API nav timing, store DNS/TCP/TLS deltas
  - `craft` → snapshot current jitter value, store as `lastCraftJitter`
  - `damage` → snapshot `effectiveType`, store as `lastDamageTier`
  - `explore` → re-run `buildTraceChain()`, store updated chain
  - `survive_night` → compute RTT drift (current RTT − RTT at dusk), store as `nightRttDrift`
- These are ZERO-REQUEST — no `fetch()` calls, just reading already-available browser APIs
- Call `samplePassive(action)` from each game system alongside `probeAction(action)`
- Display sampled values in observatory (add small readouts or tooltips)

**Step 4 — Observatory: show attack speed modifier**
- Add an "ATTACK SPEED" row in the observatory modifiers section
- Show current multiplier with trend arrow
- Show which endpoint was last probed and its RTT
- Grayed out with "swing to probe" before first attack
